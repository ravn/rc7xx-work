When a generated file embeds the value of a Make-level variable
(TRANSPORT, COMPILER, BUILD_INFO_STR, WORKLOAD, BOOT_MARK_ENABLED, ...),
**its regeneration trigger MUST be a parse-time content check**, not an
mtime dep on a stamp file or .h header.

```make
ifeq ($(filter clean cpnos-clean,$(MAKECMDGOALS)),)
_DUMMY_FOO := $(shell mkdir -p $(BUILDDIR); \
    if ! grep -q "from TRANSPORT=$(TRANSPORT)\." $(BUILDDIR)/foo.asm 2>/dev/null; then \
        { echo "; from TRANSPORT=$(TRANSPORT)."; \
          echo "..."; } > $(BUILDDIR)/foo.asm; \
    fi)
endif
$(BUILDDIR)/foo.asm: ;     # parse-time-driven, recipe is empty
```

**Why:**

Bitten twice in one session (2026-05-18):

1. `sdcc/xport_aliases.asm` (a 10-line .asm that JP-routes SNIOS to
   the PIO or SIO transport).  Dep was `xport_aliases.asm:
   transport_stamp`; some earlier `TRANSPORT=sio` run left the .asm
   newer than the stamp.  Subsequent `TRANSPORT=pio-irq` builds saw
   the asm as "up to date" → SDCC slave silently dispatched CP/NET
   to SIO-A (a file sink), polypascal hung at LOGIN.  Cost ~3 hours
   of byte-level PIO debugging looking for a timing bug that wasn't
   there.

2. `sdcc/cpnos_buildinfo.h` regenerated at 08:58 with new BUILD_DATE
   string; `cpnos_main.o` from 08:42 didn't rebuild despite the .h
   being newer, because the `prom1-lineprog` link target was invoked
   inside a sub-`$(MAKE)` whose dep tree didn't see the .h timestamp
   change for the in-progress build.  Slave ROM kept showing the
   08:42 banner across rebuilds — looked like the new build was just
   broken on display init.

Both bugs have the same shape: a generated file's *intended content*
depended on a Make-time variable, but the *regeneration trigger* was
an mtime relationship that can drift through:

- interrupted builds where the artifact gets written but the stamp doesn't
- sub-`$(MAKE)` invocations that don't re-evaluate the variable
- ad-hoc target invocations (`make foo.asm`) with override args
- parallel jobserver paths racing the stamp vs artifact write order
- a previous-session build leaving the artifact in a state the
  current-session build wouldn't recreate via its existing dep rules

**Class label:** "stale-generated-artifact-with-misleading-mtime" — a
sibling of `feedback_check_banner_timestamp.md` (which catches the
SYMPTOM on the slave-ROM side) and
`feedback_symmetric_recipes_per_compiler.md` (which catches the
build-recipe asymmetry).  This rule catches the build-system *cause*
that produces stale artifacts in the first place.

**How to apply:**

- Audit any Makefile rule of the form `$(out): $(stamp)` where stamp
  exists solely to invalidate `$(out)` on variable change.  Convert
  to parse-time content-check.
- Audit any generated header (`*_buildinfo.h`, `*_addrs.h`,
  `*_config.h`) where the content embeds a variable.  Same conversion.
- Embed a marker in every generated file that captures the relevant
  variable verbatim (e.g. `; Generated by Makefile from TRANSPORT=foo.`
  or `#define BUILD_INFO_STR "..."`).  No marker = no way to
  content-check.
- After writing such a rule, **deliberately simulate the staleness**
  (sed the embedded marker to a wrong value, run make, verify regen)
  before considering it fixed.  mtime bugs are notorious for "fixing
  themselves" on the first happy-path test only to bite later.

**Discriminator — when this rule applies:**

- Any generated file (`.h`, `.asm`, `.s`, `.ld`, ...) whose CONTENT
  varies with a Make variable that can change between invocations.
- Any build that supports multiple TRANSPORT / COMPILER / FLAVOR
  values via the same `Makefile`.

**Discriminator — when this rule does NOT apply:**

- Generated files whose content depends only on source files (their
  mtime IS the right invalidator).
- Single-variant builds where the variable never changes within the
  project's life.
- Output files where staleness doesn't affect correctness (logs,
  scratch reports).

**Diagnostic shortcut when you suspect this class:**

```sh
head -1 $(BUILDDIR)/<suspect.asm|suspect.h>
```

The embedded marker tells you what the file actually thinks it is.
If it disagrees with your current invocation, you've found it.
