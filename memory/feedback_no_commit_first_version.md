**HARD RULE: stop committing the first version of a structural fix the moment lit + size are clean.**

Lit tests + matching rcbios/cpnos-rom byte counts are a *size oracle*.  They do not detect value miscompiles.  For any change that could change which instructions are emitted for a given IR (GISel combiners, ISel patterns, legalizer changes, BooleanContents, calling conventions), run the *value oracle* before committing:

  1. **PRIMARY**: `BUILD_DIR=../../build-macos PATH="/Users/ravn/z80/z88dk/src/ticks:$PATH" cargo run -- clang -opt Oz` from `llvm-z80/z80-utils/test-runner/` — exercises real value semantics via `expect: 0xFF` style assertions at the project's ship opt level.  As of 2026-05-04 baseline: 110 PASS, 0 FAIL, 1 FATAL (alloca.h env issue), 51 SKIP.
  2a. **AUTOLOAD-IN-C MAME boot test**: `cd rc700-gensmedet/autoload-in-c && make mame` — required for ANY llvm-z80 commit because autoload-in-c exercises codegen paths (IM2 IVT setup, DMA programming, FDC multi-density detect, BSS-spill peephole sites, `+static-stack` + `+shadow-regs`) that rcbios does NOT.  Skipping this can hide regressions for weeks (session 42 lost a session+ on the BSS-spill #74 cross-pair miscompile because rcbios boot was used as the proxy).  The autoload-in-c mame target asserts on boot success (PASS / FAIL written to `/tmp/boot_test_result.txt`) and self-terminates in ~5s wall time.

  2. **SECONDARY** (BIOS-path end-to-end): MAME boot in **rcbios standalone mode** — IS a single-step value oracle.  RC702 has two boot modes: (A) **rcbios standalone**: autoload PROM in PROM 0 reads boot sector from floppy → loads rcbios + CP/M → BIOS banner ("RC700 56k CP/M 2.2 C-bios/clang <build-date>").  No host-side server needed.  Switch into mode A: `cd rc700-gensmedet/rcbios-in-c && make mame-roms-rcbios` (installs the **hand-assembled** `roa375/roa375.rom`; the C reimplementation in `autoload-in-c/` is currently broken — gets stuck in `_fdc_detect_sector_size_and_density`; see `autoload-in-c/tasks/known-bugs.md`).  Then verify: `make mame-test` and check `/tmp/screen.txt` for BIOS banner + `DISK=<hex> ERR=0` in make output.  (B) **cpnos network boot** mode requires z80pack mpm-net2 to do anything beyond the banner; only relevant when the change touches the cpnos network code path.  Switch into mode B: `cd rc700-gensmedet/cpnos-rom && make mame-roms-cpnos` (refreshes BOTH `roa375.ic66` AND `prom1.ic65` atomically — refreshing only one triggers BAD CHECKSUM black screen because the patcher's correction word in payload_b/prom1.bin won't cancel today's body sum from prom0.bin).

  3. **DEEP** (full-stack end-to-end): `cd rc700-gensmedet/cpnos-rom && make cpnos-polypascal-test`.  Drives MP/M + CP/NOS slave + PolyPascal v3 (Hejlsberg's pre-Turbo Pascal native Z80 compiler) through a primes-up-to-30000 program.  Catches transport, NDOS, BDOS, console framing, keyboard, file load, and code-execution regressions in a single ~4-minute run.  Required when a compiler change passes 1+2 but plausibly affects the cpnos network path, ISR shadow-bank handling, or BIOS-call surfaces that PolyPascal exercises (CONOUT framing, BDOS reads, keyboard injection).  Has prerequisites the harness shouldn't fight: port :4002 must be free, no stale `mpm` screen session, and `cpnos-rom` MUST have been built fresh — the make target handles the (re)start of MP/M itself, so just invoke it.  PASS gate: `/tmp/cpnos_polypascal_result.txt` starts with `^PASS`.

For pure cost-model changes (regalloc heuristics, scheduling, LICM biases that don't change which instructions are emitted, only when/where), the size oracle alone is acceptable — but err toward also running the value oracle if uncertain.

**Why:** Session 42 (2026-05-03) attempt 3 (#120 GISel combiner for `(shl 7; ashr 7)` elision from G_ICMP) committed after lit 90/90 and rcbios+cpnos-rom byte counts unchanged.  The combiner was silently incorrect: Z80's `BooleanContents = ZeroOrOne` means the shift idiom is a meaningful widen at the IR layer, not an identity.  The committed combiner+peephole composition produced byte-identical asm to baseline because peephole #26 was deleting the wrong code the combiner produced.  Disabling the peephole exposed the value miscompile (`kbstat` stored as `0x01` instead of `0xFF`).  Caught only by post-hoc MIR inspection while investigating a residual gap.  The user's rule sharpens the lesson: **the byte-count match was the trap.**  See `llvm-z80/tasks/lessons-2026-05-04-structural-fix-failures.md`.

**How to apply:**

  - After ANY combiner / ISel / lowering / GISel-area change: do not commit on lit + size pass alone.  Run `cargo run -- clang -opt Oz` and confirm the suite passes (current baseline: 110 PASS, 0 FAIL).  For BIOS-touching changes additionally do the MAME boot step in rcbios standalone mode (per item 2 above): switch with `(cd rc700-gensmedet/autoload-in-c && make prom)` then `(cd rc700-gensmedet/rcbios-in-c && make mame-test)` — IS single-step (no mpm needed).
  - When in doubt about whether a change can affect values: run the value oracle.  The cost is ~1 minute; the cost of shipping a silent miscompile is much higher.
  - When the size oracle shows "no change" for a structural fix that you expected to change something: **suspect the fix is no-op or being masked by another pass**, not "the fix is harmless."  Investigate before committing.
  - Specifically: a combiner+peephole composition that produces byte-identical baseline output is a RED FLAG for "the peephole is covering for a broken combiner."  Verify the combiner's correctness independently (disable the peephole and re-run the value oracle).
