When I notice I'm fixing **repeated instances of the same class** — or catch myself **narrating the pattern** ("same family", "recurring root", "the Nth time", "both in the same peephole"), or **filing a cluster of issues in one subsystem** — treat that as a first-class prompt to **stop and investigate the systemic cause that generates the class**, before fixing the next instance. This is the "dig UP / zoom out" complement to [[feedback_dig_deeper_before_parking]] ("dig down"). Don't wait to be told to step back.

**Why:** Session 73s — I shipped 5 same-family peephole bugs (#14/#192/#193/#195×2), wrote "same family / recurring" in nearly every commit, filed a cluster of issues in one pass (#192–#197), yet treated each as an isolated ticket and only did the systemic analysis (optimization machinery outrunning verification machinery; verifier/assertions off; production config untested) when explicitly asked. I have a strong reflex to dig *down* (root-cause before parking) but none to zoom *out* (after a cluster, ask what produces it). Worse: a "keep going" throughput loop actively suppressed it — stepping back *feels* like not-progress, so momentum won every time. The signal was in my own words and I logged it without escalating.

**How to apply:** My own pattern-naming language IS the trigger — when I write "same family / recurring / Nth instance", pause and ask "what system generates this?" After ~2–3 same-class fixes, run the global query before the next fix. The cheapest systemic remedies (test/CI/verification gaps that hide the class) usually beat any single instance fix (cf. [[feedback_extract_rules_from_time_sinks]] — but escalate past "propose a rule that catches the class" to "find what produces the class"). Even inside a "go / keep going" loop, periodically synthesize *what the batch implies*, not just *what was done*. Related: [[feedback_peephole_safety_guards]].

**Apply this to my own METHODOLOGY, not just the code (added 2026-05-26).** The zoom-out also fires when *I am repeatedly doing something the hard way* — manual bisection, chasing runtime symptoms, re-deriving the same thing — because a standard tool or build configuration is missing. Ask "is my toolchain adequate for *this kind* of work?" Concrete miss that prompted this: I root-caused miscompile after miscompile (#198 MachineCSE, the #112/#189 IY leaks) via runtime verifier FAIL + manual A/B in a **Release / assertions-OFF** clang, never flagging that an **assertions build** (`-DLLVM_ENABLE_ASSERTIONS=ON`, `-debug-only=<pass>`, `-stats`) would catch these at the offending pass. I had the knowledge; I only surfaced it when the user asked about debug flags. The recognition is the autonomous part. The action is NOT: **propose the tool/build/harness and let the user decide — do not silently stand up dev infra.** User directive 2026-05-26: keep asking before creating/modifying build configs or tooling so they stay in the loop (they explicitly declined a standing "just build dev infra yourself" authorization). So: recognize proactively, surface immediately, build only after they say go.

**Pull the tooling survey EARLIER — proactive, not just reactive (added 2026-05-26).** The trigger above is reactive ("when I'm repeatedly doing it the hard way"). There is also a proactive duty: when starting work in a domain (or when reaching for tools ad hoc), **inventory what the toolchain already offers for that kind of work and recommend the high-value ones up front** — tool discovery is my job to do before the friction, not the user's to prompt. Concrete miss (2026-05-26): the user had to ask twice — once for an assertions build, once for "other useful flags/tools?" — to extract knowledge I already had (`llvm-reduce`, `-opt-bisect-limit`, `-Rpass-missed`, `-debug-only`, `-print-changed`, `llc -run-pass`/`-stop-after`). I default to executing the task in front of me with tools already in hand, instead of asking "is there a better-equipped *way to do this whole class of task*?" The boundary stated in the paragraph above still holds (user directive 2026-05-26): proactively **survey and recommend**, but only **build/create** the tool or build config after the user says go.
